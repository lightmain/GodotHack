# BlissHack prealpha-3 开发计划

## 1. 版本目标

prealpha-3 的目标是补齐 alpha 阶段开始前仍然缺少的桌面网页版基础能力。
本版本完成后，玩家应当能够在 Settings 中管理 BlissHack 界面配置和一组
经过验证的 NetHack 配置，能够把个人配置或全部本地数据导出为文件，并且
能够在存档不兼容时取回原始存档。项目开发者应当能够使用固定工具版本重新
构建 WebAssembly 运行时，并且能够在不引入两个活动游戏会话的前提下处理
同一浏览器中的多个 BlissHack 页面。

本版本还会在独立 Git 分支中研究并实现永久背包。永久背包只有在 shim 接口、
WebAssembly 构建和桌面界面全部通过评审后才合并到主开发分支。

本版本按照以下顺序实施：

1. 统一版本信息并固定 WebAssembly 构建流程。
2. 实现 Settings、个人配置持久化以及个人配置文件导入导出。
3. 实现本地数据备份、不兼容存档救援和浏览器持久存储状态。
4. 实现多页面游戏锁。
5. 在独立分支实现永久背包。
6. 完成跨浏览器基础验证、可访问性检查、性能基线和发布验收。

这里的编号表示主要依赖顺序。阶段五的永久背包分支可以在阶段一完成后与
阶段二至四并行开发，但是不能在阶段一固定构建工具之前修改或重新生成
WebAssembly 运行时。

## 2. 术语

本计划统一使用以下名称：

- **界面配置**：只控制 React 前端如何显示和组织内容的配置。界面配置不改变
  NetHack 内核的规则、命令含义或输出内容。
- **NetHack 配置**：由 NetHack 内核读取的配置。它会改变游戏行为、输入含义
  或内核输出内容。
- **运行时配置文件**：每个 game module 启动前在 Emscripten 文件系统中提供
  给 NetHack 的 `.nethackrc` 文件。
- **个人配置文件**：玩家主动导出的 JSON 文件，其中包含界面配置和本版本支持
  的 NetHack 配置，不包含存档。
- **raw save**：NetHack 内核产生的原始二进制存档。现有 `.nhsave` 导入导出
  继续使用这种格式。
- **完整备份文件**：玩家主动导出的文件，其中包含个人配置和当前浏览器中的
  全部正式 raw save。
- **正式存档**：位于 `/save` 中、文件名符合 NetHack 正式存档规则的文件。
  “正式”只表示文件位置和命名符合规则，不表示当前构建一定能够继续该存档。
- **游戏锁**：由浏览器 Web Locks API 提供的同来源独占锁。游戏锁用于阻止
  两个页面同时运行游戏或修改同一份持久化数据。
- **永久背包**：NetHack 内核通过永久背包窗口持续提供的物品列表。该列表不是
  玩家按 `i` 临时打开的普通背包菜单。
- **构建编号**：诊断和部署使用的 Git 提交编号。
- **产品版本**：玩家可见的 BlissHack 里程碑名称，本计划对应
  `prealpha-3`。

“页面”同时包括普通浏览器标签页和将来可能出现的独立浏览器应用窗口。本版本
不实现可安装网页，但游戏锁的设计不得依赖标签页特有的行为。

## 3. 范围边界

### 3.1 本版本包含

- 单一的产品版本来源，并在 Home、诊断日志、导出文件和文档中一致使用。
- 固定 Node.js 和 Emscripten 版本。
- 自动完成 WebAssembly 清理、编译、复制和运行时文件校验的命令。
- Settings 页面及其从 Home 返回的完整导航。
- 游戏主命令等待时由 Esc 打开的暂停界面，以及从暂停界面进入 Settings。
- 三项首版界面配置：
  - 终端文字大小。
  - 消息区域保留的行数。
  - 地图是否自动保持玩家位置可见。
- 以下首版 NetHack 配置：
  - `tutorial`
  - `autopickup`
  - `pickup_types`
  - `number_pad`
  - `safe_pet`
  - `sortpack`
  - `showexp`
  - `time`
- 个人配置的浏览器持久化、恢复默认值、JSON 导出和 JSON 导入。
- 任何正式存档的原始字节导出，包括当前构建不能继续的正式存档。
- 包含个人配置和全部正式存档的完整备份文件。
- 浏览器持久存储状态展示和由玩家主动触发的持久存储申请。
- 同一浏览器配置中的多页面游戏锁。
- 永久背包 shim 能力补全、桌面侧栏和对应的两个 NetHack 配置：
  - `perm_invent`
  - `perminv_mode`
- Chromium 完整测试，以及 Firefox 和 WebKit 的基础流程测试。
- Settings、备份、多页面提示和永久背包的键盘与焦点行为检查。
- 当前版本的启动、保存、恢复和重复 game module 创建性能基线。

### 3.2 本版本不包含

- 手机或平板专用操作界面。
- 触控方向键、触控命令栏或手机软件键盘适配。
- 点击地图、怪物、物品或状态元素后显示操作菜单。
- 图块地图、Canvas、WebGL、动画特效或新的视觉资源系统。
- NetHack 游戏文本提取、翻译或多语言运行时。
- 音效、语音或音乐。
- 可安装网页、服务工作线程或离线资源缓存。
- 云端账号、云端同步或远程诊断上传。
- 修改 raw save 格式或承诺跨 NetHack 构建恢复存档。
- 自动转换不兼容存档。
- 完整 `.nethackrc` 文本编辑器。
- 任意 NetHack 配置指令的通用解析器。
- 自定义 `BIND`、`AUTOCOMPLETE`、`AUTOPICKUP_EXCEPTION`、
  `HILITE_STATUS` 或 `SYMBOLS` 图形化编辑。
- 永久背包物品的点击操作菜单。prealpha-3 的永久背包只负责稳定展示。
- 为后续手机操作提前建立另一套输入状态机。
- 后台自动保存正在运行的游戏。

### 3.3 通用约束

- React 不得在 Asyncify 等待输入期间通过额外 `ccall()` 进入 NetHack。
- Settings、备份和游戏锁不得建立第二套 game module 或游戏会话生命周期。
- NetHack 配置必须通过 NetHack 正常读取运行时配置文件的路径生效，不得直接
  写入未公开的 C 全局变量。
- 界面配置和 NetHack 配置分别保存。任何字段只能有一个持久化来源。
- 个人配置导入、完整备份导入和 raw save 导入必须使用不同的文件标识和入口。
- 所有导入文件都视为不可信输入，必须限制文件大小、字段类型、数组长度和文本
  长度。
- 完整备份导入不承诺全部成功或全部失败。每个存档复用现有单文件导入和回滚
  行为，并在结束时明确报告成功、跳过和失败数量。
- 游戏锁只负责页面之间的互斥，不负责修复浏览器崩溃、损坏存档或网络错误。
- 不支持 Web Locks API 时显示明确警告并维持当前单页面行为，不增加
  `localStorage` 心跳锁或 `BroadcastChannel` 伪锁。
- 修改任何上游 NetHack 文件时遵守 `AGENTS-cn.md` 的许可证标记、源码说明、
  shim 修改记录、重新构建和测试要求。
- 新函数必须说明用途、参数和返回值；代码注释使用英文。

## 4. 阶段一：版本信息和可复现构建

### 4.1 目的

在永久背包分支修改 C 或 shim 之前固定构建输入，减少“源码相同但开发者工具
不同”造成的运行时差异。这里的可复现构建表示构建工具和步骤可重复，不预先
承诺不同机器生成的二进制文件逐字节相同。

### 4.2 产品版本

1. 建立一个产品版本来源，值为 `prealpha-3`。
2. Home 页头、Home 页脚、诊断日志导出、个人配置文件和完整备份文件从该来源
   读取产品版本。
3. Git 提交编号继续作为构建编号。产品版本和构建编号不得互相替代。
4. 本地开发构建必须使用明确的开发构建编号；GitHub Actions 使用当前提交编号。
5. `package.json` 的 npm 包版本不作为玩家可见产品版本。
6. README 的项目状态在 prealpha-3 最终验收时更新，不在阶段一提前宣称版本
   已经完成。

### 4.3 工具版本

1. 固定 Node.js 主版本，并让本地说明与 GitHub Actions 使用同一个版本。
2. 固定 Emscripten SDK 的完整版本号，不再使用 `latest`。
3. 记录操作系统之外仍会影响构建的工具，包括 make、编译器包装脚本和 Lua
   获取方式。
4. 构建脚本在发现 Emscripten 版本不匹配时停止，并输出期望版本和实际版本。
5. 不在普通前端 CI 中每次重新编译 WebAssembly。提供手动工作流执行源码构建、
   WASM 集成测试和浏览器基础测试。

### 4.4 WebAssembly 构建命令

新增一个项目命令，按固定顺序完成：

```text
检查工具版本
清理上一次 WASM 构建产物
根据指定 hints 生成 Makefile
确认 Lua 源码存在
执行 CROSS_TO_WASM 构建
检查 nethack.js 和 nethack.wasm
同时复制两个文件到 frontend/public
生成运行时文件校验记录
运行 WASM 集成测试
```

运行时文件校验记录至少包含两个文件的 SHA-256、字节长度和生成时使用的
Emscripten 版本。SHA-256 是根据文件全部字节计算的固定摘要，用于发现只更新
一个运行时文件或文件被意外改写；它不表示存档兼容性。

`frontend/scripts/verify-runtime-assets.mjs` 在生产构建前检查：

- 两个文件都存在。
- JavaScript 文件是 Emscripten ES module。
- WebAssembly 文件具有合法文件头。
- 两个文件的 SHA-256 和字节长度与校验记录一致。

### 4.5 上游修改记录

- 建立一份 BlissHack 上游修改清单，记录修改文件、目的、对应提交和测试。
- 现有 shim 修改先补入清单。
- 永久背包分支的每项 C 修改必须有独立条目。
- 从 NetHack `upstream` 合并新提交时，先检查清单中的调用链，再重新构建
  WebAssembly。

### 4.6 自动验收标准

- 使用错误 Emscripten 版本时，构建命令在编译前失败。
- 删除或替换任意一个运行时文件时，前端生产构建失败。
- 同一次构建产生的两个运行时文件通过校验。
- 手动 GitHub Actions 工作流能够完成 WASM 构建和集成测试。
- 现有前端构建、WASM 测试和浏览器测试继续通过。

### 4.7 手动观察标准

- 新开发环境按照文档可以从源码生成可运行的浏览器版本。
- Home、诊断文件和导出文件显示相同产品版本。
- 构建失败信息能够指出缺失工具、错误版本或错误运行时文件。

## 5. 阶段二：Settings 和个人配置

### 5.1 强制设计评审门禁

实现 Settings 之前先编写
`doc/BlissHack/plans/in-prealpha-3/settings-and-profile.md`，并与用户确认。
该文档至少回答：

1. 当前 WASM 环境中 `HOME` 的值以及 NetHack 实际查找 `.nethackrc` 的路径。
2. 运行时配置文件应该位于现有 IDBFS 挂载点、独立 IDBFS 挂载点，还是每个
   game module 启动前由持久化配置生成。
3. NetHack 在游戏内写配置文件时，是否需要把变化同步回浏览器持久化配置。
4. 每个首版 NetHack 配置的准确语法、默认值、允许值和生效时间。
5. Settings 保存时如何保证界面配置和 NetHack 配置不会只写入其中一部分。
6. 个人配置文件的完整 JSON 结构、大小限制、导入校验和未来版本兼容规则。
7. 导入个人配置后，哪些字段立即生效，哪些字段从下一局开始生效。
8. 配置损坏、浏览器本地存储不可用或运行时配置文件解析失败时如何恢复默认值。

用户已于 2026-09-06 确认开始按该文档分步实施。暂停界面、游戏内 Settings
和 NetHack 配置双向同步以评审文档中的补充设计为准。

### 5.2 界面配置

首版只实现以下字段：

```ts
interface InterfaceSettingsV1 {
  terminalFontSize: "small" | "medium" | "large";
  messageLineCount: 3 | 5;
  followPlayer: boolean;
}
```

- `terminalFontSize` 只改变终端区域文字尺寸，不使用随浏览器宽度连续变化的
  字号。
- `messageLineCount` 只改变界面保留的可见消息行数，不删除 NetHack 内部消息。
- `followPlayer` 控制地图滚动区域是否在玩家移动后保持玩家位置可见。
- 每个字段都有固定默认值。
- 修改后立即应用；取消编辑时不改变当前值。
- 恢复默认值必须经过一次明确确认。
- 持久化键名包含格式版本。界面配置和 NetHack 配置可以位于同一个版本化记录
  的不同字段中，但不能共用同一个字段。

### 5.3 NetHack 配置

首版结构化编辑以下配置：

```text
tutorial
autopickup
pickup_types
number_pad
safe_pet
sortpack
showexp
time
```

- 布尔值使用开关。
- `pickup_types` 使用 NetHack 物品类别复选列表，不允许输入任意字符。
- `number_pad` 使用 NetHack 5.0 实际支持值对应的选择菜单；设计评审完成前
  不猜测数值含义。
- Settings 中显示每个配置的简短效果说明和生效时间。
- NetHack 配置在下一次创建游戏会话前写入运行时配置文件。
- 游戏内 Settings 只在核心等待主命令时修改七项允许动态修改的配置；
  `tutorial` 只影响下次新游戏。
- 图形 Settings 和 `O`、`#optionsfull`、`@` 等原生命令产生的受支持配置变化
  通过限定字段的 shim 协议双向同步，不使用 Asyncify 等待期间的额外
  `ccall()`。
- 配置文件生成顺序固定，便于测试和比较。
- 不支持的选项、重复选项和任意配置指令不得通过结构化表单写入。

永久背包合并后增加：

```text
perm_invent
perminv_mode
```

在永久背包功能合并前，这两个配置不得出现在可操作的 Settings 中。

### 5.4 Settings 界面

- Home 的 `Settings` 按钮启用并进入独立 Settings screen。
- 游戏在主命令等待状态时，Esc 打开包含 `Resume`、`Settings` 和
  `Save and Exit` 的暂停界面；其他输入状态中的 Esc 保留 NetHack 原意。
- Settings screen 使用一个页面表单，不把每个选项放进独立卡片。
- 页面分为 `Interface`、`NetHack` 和 `Profile` 三个区段。
- 布尔值使用开关，固定集合使用选择菜单，多选集合使用复选框。
- 页面提供 `Apply`、`Cancel`、`Restore Defaults`、`Export Profile` 和
  `Import Profile`。
- `Apply` 只在配置发生变化且校验通过时启用。
- 离开页面时如果存在未保存修改，显示离开确认。
- 从 Home 完成保存后返回 Home；game module 尚未调用 `main()` 时，必须确保
  下一局读取新配置。
- 从暂停界面进入 Settings 时复用同一表单；完成后返回暂停界面，并在安全命令
  边界应用当前游戏允许修改的 NetHack 配置。
- 顶层应用状态机增加 Settings 状态，并保留进入 Settings 前已经准备好的
  game module。打开或取消 Settings 不创建新 module，也不调用 `main()`。
- 所有控件具有可见标签、键盘焦点和错误说明。

### 5.5 个人配置文件

个人配置文件使用 UTF-8 JSON，建议扩展名为 `.bhprofile`，文件标识固定为
`blisshack-profile`。结构至少包含：

```json
{
  "format": "blisshack-profile",
  "schemaVersion": 1,
  "productVersion": "prealpha-3",
  "exportedAt": "ISO-8601 timestamp",
  "interface": {},
  "nethack": {}
}
```

- 文件上限为 1 MiB。
- `schemaVersion` 不受支持时拒绝导入，不猜测字段含义。
- 同一结构版本中的未知字段忽略，但不写入浏览器存储。
- 每个已知字段分别校验类型和允许值。
- 导入前显示将改变的字段，玩家确认后才保存。
- 文件不包含角色名、存档、诊断日志、构建路径或浏览器信息。
- 导入失败时现有配置保持不变。
- 从 Home 导入成功后界面配置立即生效，NetHack 配置按新游戏和继续存档规则
  生效；游戏中导入时，七项动态配置在安全命令边界应用，`tutorial` 从下次
  新游戏开始生效。

### 5.6 单元测试要求

- 缺失字段使用默认值。
- 类型错误、非法枚举值、超长数组和不支持的结构版本被拒绝。
- 浏览器本地存储抛错时应用使用默认配置，Settings 仍可打开。
- 修改一个字段不会改变其他字段。
- `Cancel` 不写入持久化存储。
- `Apply` 失败时保留应用前的完整配置，不产生部分更新。
- 配置文件导出后重新导入得到相同配置。
- 导入失败不会产生部分更新。
- 运行时配置文件内容顺序固定，并且只包含允许的 NetHack 配置。
- 新游戏启动前能够读取刚保存的 NetHack 配置。
- 游戏内原生命令修改受支持配置后，图形 Settings 显示核心回报的实际值。
- 恢复存档后的初始配置快照不会静默覆盖个人默认配置。

### 5.7 自动验收标准

- Playwright 修改界面配置，刷新后仍然生效。
- 导出个人配置，恢复默认值，再导入后恢复原配置。
- 修改 `tutorial` 后，新游戏按照该值进入对应流程。
- 修改 `number_pad` 后，方向输入仍然符合 NetHack 当前模式。
- 个人配置 JSON 可以解析且不包含玩家名、存档或诊断内容。
- Settings 的键盘导航、保存、取消和离开确认测试通过。
- Esc 只在主命令等待时打开暂停界面；Resume 不向核心发送输入。
- `Save and Exit` 与键盘 `S` 使用相同的确认、保存、flush 和退出流程。
- 游戏内图形修改与原生命令修改能够双向同步。

### 5.8 手动观察标准

- Settings 与 Home 的导航没有创建游戏会话或调用 `main()`。
- 每个配置名称、说明和控件之间关系明确。
- 界面配置生效时没有明显布局跳动或文字重叠。
- 配置文件可以在另一个全新浏览器配置中导入。

## 6. 阶段三：本地数据备份和存档救援

### 6.1 目的

让玩家能够在清除网站数据、迁移设备或版本不兼容之前取回自己的数据。本阶段
不改变 raw save，也不承诺当前构建能够继续旧版本存档。

### 6.2 不兼容存档救援

- 存档列表继续区分“可以继续”和“不能继续”。
- 只要文件是 `/save` 中符合正式存档命名规则的普通文件，就允许导出原始字节。
- fingerprint 不匹配、header 截断或角色身份不能解析时，`Continue` 保持禁用。
- 导出不需要把文件伪装成有效存档，也不修改文件。
- 无法解析角色名时，下载文件名使用不含路径信息的稳定替代名称。
- 删除行为继续保留二次确认。
- 错误信息明确区分“不兼容”和“损坏或无法识别”，但不声称能够自动修复。

### 6.3 完整备份文件

完整备份文件使用 UTF-8 JSON，建议扩展名为 `.bhbackup`，文件标识固定为
`blisshack-backup`。文件包含：

- 结构版本。
- 产品版本和构建编号。
- 导出时间。
- 一份个人配置。
- 每个正式存档的原始文件名、字节长度、SHA-256 和 Base64 字节文本。

Base64 是把二进制字节编码为 JSON 字符的固定方式。它会增加文件大小，但当前
NetHack 存档很小，本版本不为此引入 ZIP 依赖。

完整备份文件不包含诊断日志、浏览器地址、IndexedDB 内部记录或临时文件。
输入文件最多包含 100 个存档，解码后的存档总大小不超过 64 MiB，JSON 文件
大小不超过 96 MiB。

### 6.4 完整备份导出

- 只能在 Home 或 Settings 中导出。
- 导出前等待当前 storage operation 完成。
- 枚举当前 `/save` 中的全部正式存档，包括不能继续的正式存档。
- 对每个存档计算 SHA-256。
- 任意文件读取失败时停止导出并显示错误，不生成缺少文件的“完整”备份。
- 没有存档时仍可导出只包含个人配置的完整备份。

### 6.5 完整备份导入

- 只能在没有活动游戏会话时导入。
- 导入前校验文件标识、结构版本、总大小、存档数量、单文件大小、Base64 和
  SHA-256。
- 路径只接受正式存档文件名，不接受 `/`、`\`、`..` 或绝对路径。
- 导入前显示个人配置变化、可导入存档、不兼容存档和同名冲突。
- 玩家逐项决定同名存档是否覆盖。
- 当前构建兼容的存档复用 prealpha-2 已有 raw save 导入流程。
- 当前构建不兼容的存档不写入当前存储；备份文件仍保留它的原始字节。
- 每个存档独立报告成功、跳过或失败。不建立跨全部文件的持久事务。
- 某个存档失败时继续处理玩家已经确认的其他存档，最后显示汇总。
- 个人配置在存档处理结束后单独确认应用；失败的存档不会造成配置自动回滚，
  界面必须分别报告两个结果。

### 6.6 浏览器持久存储

- Settings 显示浏览器当前是否已经授予持久存储。
- 玩家可以点击 `Protect Local Data` 调用
  `navigator.storage.persist()`。
- 浏览器不支持、拒绝或抛错时显示准确结果，不循环请求。
- 获得持久存储只表示浏览器不会因为磁盘压力主动清理该来源的数据。
- 界面必须说明玩家主动清除网站数据、删除浏览器配置或更换网站来源仍会删除
  或隔离本地数据。
- 不把持久存储状态描述为云备份。

### 6.7 清除本地数据

- Settings 提供 `Clear Local Data`。
- 确认对话框分别列出将删除的存档、个人配置和诊断日志。
- 玩家必须输入固定确认文本后才能执行。
- 清除前提供 `Export Full Backup`。
- 清除操作只在没有活动游戏会话时执行。
- 删除和同步成功后重新创建干净 game module，再回到 Home。
- 清除失败时进入可恢复错误或 fatal 的分类沿用 prealpha-2 诊断规则。

### 6.8 测试要求

- 不兼容正式存档可以导出，但不能继续。
- 完整备份中的每个 SHA-256 与解码后字节一致。
- 备份文件路径穿越、重复路径、重复角色、超限数量和超限大小被拒绝。
- 完整备份导出后，在全新浏览器上下文导入，个人配置和全部兼容存档恢复。
- 某一个存档导入失败时，其他已成功存档仍可继续，汇总数字准确。
- 持久存储 API 的 granted、denied、unsupported 和 throw 路径都有测试。
- 清除操作不会删除其他网站数据，只清除 BlissHack 管理的键和值。

## 7. 阶段四：多页面游戏锁

### 7.1 目的

阻止同一个浏览器配置中的两个 BlissHack 页面同时运行游戏或修改持久化数据。
本阶段使用浏览器 Web Locks API，不实现依靠过期时间和定时心跳猜测页面状态的
锁。

### 7.2 游戏锁规则

锁名固定为：

```text
blisshack.active-game-and-storage
```

规则如下：

1. Home 的只读显示和诊断日志导出不持有游戏锁。
2. 开始新游戏和继续游戏前请求独占游戏锁。
3. 游戏会话从认领 game module 到退出同步与清理完成期间一直持有游戏锁。
4. raw save 导入导出、存档删除、个人配置保存与导入导出、完整备份导入导出
   和清除本地数据短暂持有同一个游戏锁。
5. 获得任何游戏锁后，开始游戏或执行存档操作之前都先重新读取持久化存储。
   不能继续使用获得锁之前枚举的存档内容。
6. 另一个页面持有活动游戏锁时，不允许导出存档或完整备份，避免把尚未保存
   的旧持久化版本误认为当前游戏进度。诊断日志仍然可以导出。
7. 申请锁失败时，不启动游戏、不调用 `main()`、不读取用于导出的存档，也不
   写文件。
8. 正常退出、fatal 清理、页面关闭和浏览器崩溃后由浏览器释放锁。
9. 本版本不提供“强制夺取锁”。玩家可以关闭另一个页面后重试。

### 7.3 不支持 Web Locks API

- Home 显示“当前浏览器不能保护多页面游戏”的 warning。
- 单页面新游戏、继续和存档操作仍然可用。
- 诊断日志记录一次 `game_lock.unsupported`。
- 不使用 `localStorage`、IndexedDB 时间戳或 `BroadcastChannel` 模拟锁。
- Firefox 和 WebKit 基础测试记录实际支持情况，不能仅根据浏览器名称判断。

### 7.4 界面行为

- 另一个页面持有游戏锁时，点击 New Game、Continue 或任意个人配置与存档
  文件操作会显示对话框。
- 对话框说明另一个 BlissHack 页面正在运行游戏或修改数据。
- 提供 `Try Again` 和 `Cancel`。
- 不持续轮询，不显示不准确的剩余时间。
- 锁释放后 `Try Again` 能够继续原操作。
- 锁冲突属于可恢复 warning，不进入 fatal。

### 7.5 测试要求

- 同一浏览器上下文打开两个页面，只有一个页面能够开始游戏。
- 第二个页面锁失败时没有创建 session，也没有调用 `main()`。
- 第一页正常退出后，第二页重试能够开始游戏。
- 第一页发生 fatal 并完成清理后释放锁。
- 活动游戏期间，第二页不能导入、导出或删除存档，也不能导入或导出完整备份。
- 获得锁后重新枚举存档，不使用第二页先前加载的旧列表内容。
- 两个页面同时请求短存储操作时严格串行执行。
- Web Locks API 缺失时显示 warning，并且单页面流程仍通过。

## 8. 阶段五：永久背包独立分支

### 8.1 强制设计评审门禁

永久背包在独立 Git 分支开发。修改 C、shim 能力位或 WebAssembly 产物之前，
先编写
`doc/BlissHack/plans/in-prealpha-3/permanent-inventory.md`，并与用户确认。
文档至少回答：

1. `WC_PERM_INVENT`、`perm_invent` 和 `perminv_mode` 在 NetHack 5.0 中的
   准确调用链。
2. 当前 `shim_procs.wincap` 为什么没有声明 `WC_PERM_INVENT`。
3. `can_set_perm_invent()` 拒绝启用时的准确行为。
4. `shim_update_inventory()`、`repopulate_perminvent()` 和 Asyncify 重入之间
   的关系。
5. 永久背包窗口的创建、清空、填充、结束、更新和销毁顺序。
6. 如何区分永久背包菜单与临时物品选择菜单。
7. 永久背包更新是否会触发 `select_menu()`，以及前端应当如何处理
   `PICK_NONE`。
8. 当前 shim 是否只缺少能力声明，还是还缺少窗口信息、行为回调或模式限制。
9. 所需上游 C 修改的最小范围。
10. 永久背包开启、关闭、切换模式和恢复存档时的测试方案。

用户确认文档前，不得只添加 `WC_PERM_INVENT` 能力位并假定功能完整。

### 8.2 分支和合并规则

- 分支从完成阶段一的主开发分支创建。
- 分支只包含永久背包所需的 C、shim、WASM、React、测试和文档修改。
- 不在该分支同时实现 Settings 主体、完整备份或多页面游戏锁。
- 每项上游修改在源文件中注明 BlissHack 修改者、日期和目的。
- 同步更新 `doc/BlissHack/shim-interface-reference.md` 的行为差异和调用链。
- 同时更新 `frontend/public/nethack.js`、`frontend/public/nethack.wasm` 和
  运行时校验记录。
- 合并前执行完整代码评审和全部自动测试。

### 8.3 桌面永久背包界面

- 永久背包作为游戏页面的独立侧栏，不作为 modal。
- 默认位于地图右侧；窄桌面宽度下可以位于地图下方。
- 侧栏不覆盖消息、地图、状态栏或输入对话框。
- 每个物品显示 NetHack 提供的文本、数量、选中状态、物品字符和可用 glyph。
- 当前装备或使用状态只根据 NetHack 提供的数据展示，不从文本猜测。
- 更新同一个永久背包窗口时替换对应列表，不创建重复侧栏。
- 临时 `PICK_ONE` 和 `PICK_ANY` 菜单继续显示为 modal。
- 永久背包关闭后清除侧栏，不保留上一局物品。
- prealpha-3 不为物品增加点击操作菜单、说明文字或拖放。

### 8.4 Settings 集成

- 永久背包功能合并后，Settings 增加 `perm_invent` 开关。
- `perminv_mode` 使用 NetHack 5.0 实际允许值对应的选择菜单。
- 永久背包侧栏位置、宽度和折叠状态属于界面配置。
- `perm_invent` 和 `perminv_mode` 属于 NetHack 配置。
- 关闭 `perm_invent` 后不显示空侧栏。

### 8.5 测试要求

- 原生 libnh 或 WASM 测试证明能力声明和调用顺序符合 NetHack 契约。
- 启用永久背包后，开始游戏能够创建并填充唯一侧栏。
- 拾取、丢弃、装备、卸下和数量变化会更新列表。
- 普通背包菜单与永久背包同时存在时互不覆盖。
- `perminv_mode` 的每个支持值产生预期内容范围。
- 保存并继续后永久背包恢复。
- 退出第一局后开始第二局，不残留第一局物品。
- 更新永久背包期间没有 Asyncify 重入。
- 关闭永久背包后现有游戏流程和 15 条 prealpha-2 浏览器测试无回归。

## 9. 阶段六：兼容性、可访问性、性能和发布验收

### 9.1 浏览器测试

- Chromium 继续运行全部单元、WASM、普通浏览器和长流程测试。
- Firefox 和 WebKit 各增加一组基础浏览器测试：
  - 打开 Home。
  - 开始新游戏。
  - 保存并返回。
  - 刷新并继续。
  - 导出和导入个人配置。
  - 导出 raw save。
  - 检查 Web Locks API 实际支持情况。
- Firefox 和 WebKit 测试先放入手动 GitHub Actions 工作流。连续稳定后再决定
  是否加入每次 push。
- 不因为某个浏览器不支持可选持久存储申请而判定游戏不可运行。

### 9.2 可访问性

- Settings、个人配置导入、完整备份导入、锁冲突和清除数据对话框具有明确名称。
- 打开对话框后焦点进入对话框，关闭后返回触发按钮。
- Tab 和 Shift+Tab 不会把焦点移到 modal 后方。
- 错误信息与对应控件建立程序关联。
- 开关、选择菜单和复选框具有可读标签，不能只依赖颜色表达状态。
- 永久背包侧栏具有标题，并能够通过键盘滚动。
- 本版本不要求屏幕阅读器逐格朗读字符地图；地图的完整可访问性方案留到
  alpha 图形与交互设计阶段。

### 9.3 性能基线

在固定测试机器和 Chromium 版本上记录：

- 首次导航到 Home 可操作所需时间。
- 点击 New Game 到出现第一个名字输入所需时间。
- `nethack.js`、`nethack.wasm` 和前端构建资源的字节长度。
- 保存、刷新和继续所需时间。
- 连续创建并退出 20 个 game module 前后的 JavaScript heap 观察值。
- 永久背包包含 20、100 和 300 个条目时的更新与滚动表现。

性能数据写入发布验收文档，不设置依赖共享 CI 机器绝对耗时的硬门槛。以下行为
必须视为缺陷：

- 每次 game module 结束后仍保留新的全局 callback。
- 重复会话造成页面持续变慢。
- 永久背包更新导致输入明显阻塞。
- Settings 修改造成地图或对话框尺寸持续抖动。

## 11. 阶段交付和评审点

- 阶段三实现前，确认完整备份文件结构和逐文件导入结果规则。
- 阶段四实现前，确认多页面锁冲突时哪些只读操作仍然允许。
- 阶段五修改 C 或 shim 前，确认永久背包调用链和最小接口修改。
- 永久背包分支合并前，单独执行代码评审、WASM 重建和人工游玩。
- 阶段六完成后，执行全部自动测试和手动最终验收。

## 12. prealpha-3 完成定义

只有同时满足以下条件，prealpha-3 才算完成：

- 产品版本和构建编号在所有玩家可见位置一致。
- 固定工具版本能够重新生成成对的 WebAssembly 运行时文件。
- Settings 可以可靠保存、恢复默认值、导出和导入个人配置。
- 首版界面配置和 NetHack 配置按照规定的生效时间工作。
- 当前构建不能继续的正式存档仍然能够导出原始字节。
- 完整备份能够恢复个人配置和所有当前构建兼容的存档。
- 持久存储状态和限制向玩家说明清楚。
- 支持 Web Locks API 的浏览器中，同一浏览器配置不能同时运行两个活动游戏
  会话；不支持时必须显示明确 warning。
- 永久背包通过正式 shim 流程持续更新，不产生 Asyncify 重入。
- prealpha-3 没有引入手机交互、图形地图、翻译、音频或 PWA。
- Chromium 完整测试以及 Firefox、WebKit 基础测试通过。
- 用户完成手动最终验收。
